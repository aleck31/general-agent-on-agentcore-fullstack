# AgentCore Runtime + Gateway — measured behavior notes

Facts about how AgentCore Runtime and Gateway actually behave, established by direct measurement against a deployed probe MCP server (`probe/` — a minimal server whose `whoami` reports a process-start instance id, a per-process call counter, and the request headers it received). These are behaviors the AWS docs leave implicit; recording them so they aren't rediscovered the hard way. Account-specific ids and raw run data live in the team's local working notes, not here.

Scope: **platform behavior an agent developer trips over** — session and microVM lifecycle, cold start, timing, the Runtime/Gateway APIs, and the one credential-delivery limit that shapes this repo's topology. The **Lark identity integration itself** — per-hop reasoning, the full 3LO narrative, vendor coverage, the debugging history — is the subject of the two sibling samples: [sample-lark-identity-on-agentcore-native](https://github.com/aws-samples/sample-lark-identity-on-agentcore-native) and [sample-lark-identity-on-agentcore-interceptor](https://github.com/aws-samples/sample-lark-identity-on-agentcore-interceptor).

## Session & microVM lifecycle

- **A microVM is per session, 1:1 — and the isolation is real, but only one kind of evidence proves it.** Same session across calls lands on the same microVM; different sessions get different ones, concurrently as well as serially.
  - **Identifiers cannot prove this.** Anything captured in the image or snapshot is copied to every restore. Measured on three *concurrent* sessions: the kernel's `boot_id` was **identical** for all three, and `pid` was `1` in each. Neither means they share a machine — a self-generated uuid, a boot id, a pid: all reproduce identically across restores of one image.
  - **Post-start writes do prove it.** Each of the three sessions wrote a marker file to `/tmp` and then listed the directory: each saw only its own. Runtime state cannot be copied from a snapshot, so this establishes separate filesystems — consistent with the documented dedicated-microVM-per-session guarantee. Use this shape of test, not identifier comparison.
  - A serial test is not enough either way: it can't distinguish "dedicated" from "one microVM reassigned after the previous session ended".

- **Gateway sessions are opt-in.** Unless the gateway is created with `protocolConfiguration.mcp.sessionConfiguration.sessionTimeoutInSeconds` (900–28800), the `initialize` response carries **no** `Mcp-Session-Id` header, and every `tools/call` cold-starts a fresh downstream microVM. With it configured, `initialize` returns an `Mcp-Session-Id`; the client must echo it on every later request to get warm-microVM reuse.

- **`time.time()` inside the microVM is NOT wall-clock elapsed time — do not build timing on it.** Measured: a process reported 777 s of age (`time.time()` at module import vs. now) inside a kernel that had been up for **25 s**. A process cannot outlive its kernel, so the wall clock's base is inherited from the image the microVM restores from, not set at boot. This one flaw produced a chain of wrong conclusions here (a "22-minute-old process serving a one-minute-old session", and from it an invented warm pool) before `/proc/uptime` exposed it. AWS's devguide mentions no pre-warming at all — checked `runtime-lifecycle-settings`, `runtime-how-it-works`, `runtime-sessions`, 25–39 kB each, zero hits for "warm pool"/"pre-warm"/"warm instance".
  - **Use `time.monotonic()` for durations and `/proc/uptime` for the microVM's age.** Both were verified to advance with real time (70 s of waiting → +70 s on each). After switching, process age became sane (5 s → 75 s across a 70 s gap).
  - Three distinct figures, easy to confuse — `agent/server.py` reports all three and `/status` shows the last two: process age (`monotonic`, when this process started), **microVM age** (`/proc/uptime`, the only answer to "how long has this compute been running"), and **session age** (from the first request bearing this session id — independent of when the microVM booted).

- **The session id reaches the container.** AgentCore sends `x-amzn-bedrock-agentcore-runtime-session-id` on every `/invocations` request (verified by echoing headers back). That is what lets a process report per-session age rather than only its own.

- **Cold start is measurable, with caveats.** `microVM age − session age` is how long the compute was up before your request arrived: near zero means it started for you. AgentCore's own provisioning time stays invisible (no instance API), so only X-Ray segments (untested here) or end-to-end deltas can bound it. A fresh session id does **not** imply a cold start. To make cold starts repeatable, drop `idleRuntimeSessionTimeout` to its 60 s minimum for the test.

- **Cold start is ~19 s, and essentially none of it is ours.** Measured on this deployment by timing the module's own imports against `/proc/uptime` and logging the split at start-up (`agent/server.py:_log_startup_breakdown`, log-only): `microVM=19.6s process=0.5s imports=0.5s before-our-code=19.1s`, reproduced across two cold starts within 0.1 s. So ~97% is AgentCore booting the microVM and pulling the image before our code runs; trimming imports would buy back half a second. Optimising cold start is not an application-layer problem here. (Measured while the agent was on Strands; the import set is LangGraph now, and the 19 s before our code is unaffected either way — re-measure the 0.5 s import share if you care about it.)
  - AWS documents none of this. The only statement on the subject: without a consistent session id "each request may be routed to a new microVM, which may result in additional latency due to cold starts" (`runtime-sessions`) — no phases, no figures.
  - **X-Ray cannot see it either.** Its trace root is the agent's own segment, so everything before OTel initialises (kernel boot, image pull, imports) is outside the trace — verified against a real trace, whose only child was the agent's Cognito call. Contrast Lambda, which splits INIT/INVOKE server-side and emits an `Initialization` subsegment. So `microVM age − session age` bounds the total, and only in-container instrumentation breaks it down.

- **Session create/tear-down returns a retryable 409.** "While the service provisions or tears down a session, a second operation targeting that same session returns a retryable HTTP 409 `RetryableConflictException`... Retry with short exponential backoff." Relevant here because the router disables botocore retries outright (a timeout must not replay a whole turn), which also means nothing retries a 409.

- **Probing a session id is not a passive read.** Calling `status` on an id with no live microVM provisions one — measured at 1.4 s for a fresh id. `/status` therefore materialises part of what it reports.

- **Within a session, the microVM and its MCP server process are reused — not cold-started per call.** Measured: 5 consecutive calls on one session hit the same instance id with a per-process counter incrementing 1→5. The first call for a target pays the cold start + MCP `initialize`; later same-session calls skip both. The two lifecycle limits govern different things, and only one is resettable:
  - `idleRuntimeSessionTimeout` (default 900 s / 15 min) — **session inactivity**. Reset on every invocation, so it only fires after a quiet stretch. This is the one `HealthyBusy` defers.
  - `maxLifetime` (default 28800 s / 8 h) — **wall-clock age of the microVM from creation**, not the session. It never resets *for that microVM*, so a continuously busy turn is still cut off at 8 h and `HealthyBusy` does not help. This is the hard ceiling on a single background task. It is not a ceiling on the session, though: once the microVM is gone the next invocation gets a new one "with the same lifecycle configuration (i.e. `idleRuntimeSessionTimeout` and `maxLifetime` that can be up to **another 8 hours**)" — so a session can outlive many 8-hour compute lifetimes. Still leave margin on any one turn: we could not establish whether a microVM's clock starts before it is assigned to a session.

Both are configurable 60–28800 s via `lifecycleConfiguration` and left at defaults on every Runtime here. On either limit the `runtimeSessionId` survives — the next call provisions a fresh microVM (sanitized memory, cold start), and the session stays valid until the Runtime ARN is deleted. Since memory bills continuously across a session including idle, a shorter idle timeout is the direct lever on idle cost.
  - Sources: <https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-lifecycle-settings.html> (timer semantics: idle resets per invocation, `maxLifetime` "cannot be reset"), <https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html> (Stopped → Active with new compute), <https://aws.amazon.com/bedrock/agentcore/pricing/> (billing spans boot → idle → termination; memory continuous, CPU only during active processing).

- **Two deployment artifacts; both run in microVMs.** `CreateAgentRuntime.agentRuntimeArtifact` accepts either `containerConfiguration` (an ECR image URI) or `codeConfiguration` (source in S3 + `runtime` + `entryPoint`; runtime enum as of 2026-08: `PYTHON_3_10`…`PYTHON_3_14`, `NODE_22`). "Container" is the packaging; the microVM is the isolation boundary, and the Runtime docs never use "container" for the isolation unit. This deployment uses `containerConfiguration`. Read from the live `bedrock-agentcore-control` API model and verified against the deployed agent Runtime.

- **`runtimeSessionId` ≠ user.** AgentCore does not enforce a session-to-user mapping; the caller owns it. When a **Gateway** is the caller, it derives the session from the inbound JWT identity — so two end users get two gateway sessions and two downstream microVMs, each stable within its own session, with no extra work.

## Runtime API semantics

- **`UpdateAgentRuntime` replaces rather than patches.** Setting the authorizer without resending `environmentVariables` silently cleared all of them; the symptom was a `ValidationException` from `GetResourceOauth2Token` about a missing `ResourceOauth2ReturnUrl`. Read the current config back and resend artifact, role, network and env together — `scripts/provision.sh` does this, and aborts if the live runtime reports no env vars to preserve.
- **`CUSTOM_JWT` and SigV4 invocation are mutually exclusive, and the error says so plainly**: `AccessDeniedException: Authorization method mismatch. The agent is configured for a different authorization method than what was used`. So a caller's switch to `Authorization: Bearer` and the authorizer change are one cutover, not additive hardening.
- **`authorizerConfiguration` has exactly one shape**, `customJWTAuthorizer` (`discoveryUrl` + `allowedAudience`/`allowedClients`/`allowedScopes`, plus optional custom claim matching) — verified from the `create-agent-runtime` API model. `UpdateAgentRuntime` accepts it, so switching inbound auth does not require rebuilding the runtime.
- **A consent stops being retrievable, and a chat surface hides it by answering from history.** Measured on one consented user: `GetResourceOauth2Token` returned the token and the MCP server logged four `tools/call token=yes` right after consent; hours later the same call — same Runtime, same container, same actor, same opaque workload token (fingerprint `len=2975 sha=65cfd6ad8b04`), same provider, scopes, `customState` and `forceAuthentication` — returns only `authorizationUrl`, repeatably, and an immediate retry does not change it. Ruled out along the way: the vault namespace (`ForUserId` and `ForJWT` both empty from outside a Runtime), the scope set (requested, granted, none), `customState`, warm-vs-cold containers, in-process session caching, and the shim's token response (its refresh grant is exercised and succeeds — `grant=refresh_token`, fresh 7199s token — so AgentCore *is* refreshing something).

  **RESOLVED — it was two of our own bugs, and neither was where the symptom pointed.** The visible failure had moved one step earlier, to `CompleteResourceTokenAuth` answering `AccessDeniedException: Invalid or expired session` on a session **7 seconds old** (`authorize` 10:11:14, shim `/return` 10:11:19, rejection 10:11:21) — so not time expiry, and not a regression, since that call site had not changed since a consent that did succeed. What finally settled it was logging the **pending session id** on both sides; until then every explanation was a guess, and two of mine were wrong.

  1. **A consent link minted with `forceAuthentication=False` cannot be completed.** `GetResourceOauth2Token` returns an `authorizationUrl` either way, but only the forced one produces a session `CompleteResourceTokenAuth` accepts. Correlated end to end: of the four sessions minted for one user, the one the router completed successfully (`79e35621-…`) was a `force=True` session, and a `force=False` fetch right afterwards returned a real token. This is why `/auth lark` always worked (its `reauth` path forces) while an ordinary turn's implicit consent never did. Forcing is safe **only when the vault is empty** — there is no grant to lose.

  2. **A wrong-actor fetch used to destroy the caller's own grant.** The vault is keyed by the caller's workload identity, not by the actor named in the request, so a fetch for a bogus actor returns *the caller's* token; the ownership check then failed and the code forced a fresh flow to "clear the stale grant" — which wiped a working one. Measured directly: a token at 13:16:40, `authorizationUrl` at 13:16:41, and every later fetch for the real user refused. A mismatch now returns `wrong_owner` and mints nothing.

  A third fault made the first one harder to see: the retry that works around `GetResourceOauth2Token`'s nondeterminism built a second session and handed back the **first** one's URL, i.e. a link its own retry had just invalidated. It now keeps the newest.

  What made this hard to see is worth more than the bug: **`chat` looked healthy while the tool was never called.** It replied with the user's real document names from the checkpoint thread, because the earlier genuine listing is in the history — no `tools/call` reached the MCP server at all. Only the AG-UI surface, which refuses to run without a token, reported the truth. So a working-looking reply is not evidence that per-user identity is working; the MCP server's own `tools/call token=yes|no` log is. Check that before believing a chat transcript.



- **The workload identity the Runtime hands the container is a different vault namespace from `GetWorkloadAccessTokenForJWT`.** Under `CUSTOM_JWT` the platform delivers a workload access token derived from the inbound JWT, and a consent opened with it is vaulted against *that* identity. Re-deriving one yourself from a freshly minted JWT for the same user — same `sub`, same Cognito user — reads a different namespace and finds nothing. Measured: after a real consent the agent called Lark successfully with a user token four times (`tools/call token=yes` on the MCP server) while the router's own `GetResourceOauth2Token` kept returning `authorizationUrl` and no `accessToken`, for both `ForUserId` and `ForJWT`, with the requested scopes, the granted scopes, and none. So whichever component opens the consent must also be the one that reads it back; a second component cannot check "is this user authorised" by asking the vault itself. Note also that `Secrets Manager` shows no user-grant secret at all — the vault holds only the provider's own client secret, unchanged since creation — so the absence of a secret is not evidence about whether a grant exists.
- **`serverProtocol` is `MCP | HTTP | A2A | AGUI`, and a plain `HTTP` runtime already streams.** AgentCore proxies a streamed response through `/invocations` unchanged: a container writing `text/event-stream` has each chunk arrive as it is written (measured — three events written a second apart arrived at +1.19s, +2.11s, +3.11s, with the content type preserved). So the AG-UI contract does not require a second runtime declared `AGUI`; it can be served from the existing `HTTP` one, which is worth knowing because every extra runtime bills idle memory-time. What `AGUI` buys instead is the platform validating the AG-UI shape and the tooling (`agentcore add agent --protocol AGUI`) — not the streaming itself.

- **Under `CUSTOM_JWT`, the Runtime delivers a workload access token to the container itself**, derived from the verified inbound JWT — no manual exchange call. It arrives in **three header aliases with the same value** (2911 bytes in our case): `x-amzn-bedrock-agentcore-runtime-workload-accesstoken`, `x-amz-bedrock-agentcore-identity-wat`, `workloadaccesstoken`. Read whichever is present; do not assume one name. `Authorization` reaches the container too, but only if `requestHeaderConfiguration.requestHeaderAllowlist` includes it — the WAT headers arrive regardless.
- **Custom passthrough headers are stripped unless allowlisted.** `requestHeaderAllowlist` on the tool Runtimes is what lets `X-Amzn-Bedrock-AgentCore-Runtime-Custom-Lark-Token` reach the container at all (`scripts/build-mcp.sh`).

## Code Interpreter, and mounting per-user storage into it

All measured in this account on 2026-09-17 against a throwaway rig (bucket + S3 Files file system + two Access Points + a VPC with no NAT), then torn down.

- **`filesystemConfigurations` requires VPC network mode.** `StartCodeInterpreterSession` with a mount under `networkMode=SANDBOX` fails outright: `ValidationException: VPC network mode is required when filesystemConfigurations are provided`. So "sandbox reaches S3 without a VPC" is true for the *API* and false for a *mount*.
- **But the mount needs no NAT.** A VPC with private subnets, a **free S3 gateway endpoint** and `vpcConfig.requireServiceS3Endpoint=true` was enough: the session started, mounted, and ran Python 3.12.13 on ARM64. This is the important difference from putting the *Runtime* in a VPC (ADR 0007), where NAT was unavoidable because the Runtime itself must keep reaching Bedrock, Lark and a cross-region Gateway.
- **Per-session mounts work even when the resource declares none.** One shared `CodeInterpreter` (created with no `filesystemConfigurations`) accepted a different Access Point per `StartCodeInterpreterSession`. That is what makes per-user isolation cheap: one resource, one Access Point per user, and the boundary is the microVM's rather than our code's.
- **Isolation holds.** A session mounting user B's Access Point saw an empty `/mnt/user` while user A's files existed; `ls /mnt/user/../` shows only `user`, so the Access Point root is the top of the visible tree. Ownership follows the Access Point's `posixUser` (`drwx------`, uid 1000).
- **`mountPath` must match `/mnt/[a-zA-Z0-9._-]+/?`.** Anything else is a validation error, so `/workspace` is not available — this project uses `/mnt/workspace`.
- **Mounting needs `ClientMount`/`ClientWrite` on the execution role**, in both the `s3files:` and `elasticfilesystem:` namespaces (S3 Files runs on the EFS control plane). Without them the session refuses to start with `S3 Files mount failed: access denied. Verify your execution role has the required mount permissions` — a start-time failure, not a runtime one, so it cannot be mistaken for a code problem.
- **`readFiles`/`writeFiles` cannot touch the mount.** They are scoped to the sandbox's own workspace (`/opt/amazon/genesis1p-tools/var`), and an absolute path is rejected with `Invalid file path: potential path traversal detected`. Read and write mounted files with `executeCommand`/`executeCode` instead; copying between workspace and mount works normally.
- **Write-through to S3 is asynchronous — measured ~40 s** for a small file to appear as an object. Directories appear promptly, files lag. So delivering an artifact by reading the bucket needs a wait or a retry; reading it back through the sandbox does not. The file system's sync config also carries `importDataRules.sizeLessThan=131072` and `expirationDataRules.daysAfterLastAccess=30`.
- **Session shape:** own microVM, 2 vCPU / 8 GB / 10 GB disk, default timeout 900 s and up to 28,800 s, session data retained 30 days, 100 MB inline payload, 1,000 concurrent sessions per account. Languages: Python, JavaScript, TypeScript (JS/TS default to `deno`).
- **API shapes worth knowing before writing code:** `CreateFileSystem` needs the bucket **ARN** and a role trusted by `elasticfilesystem.amazonaws.com`, and refuses a bucket without versioning (`Your bucket must have versioning enabled`). `CreateAccessPoint`'s `rootDirectory` takes `creationPermissions`, **not** EFS's `creationInfo`. `InvokeCodeInterpreter` actions: `executeCode`, `executeCommand`, `readFiles`, `writeFiles`, `listFiles`, `removeFiles`, plus async `startCommandExecution`/`getTask`/`stopTask`.
- **Teardown gotcha:** deleting the mount targets leaves AWS-managed ENIs (`ela-attach-…`, owner `amazon-aws`) attached in the subnets. They cannot be detached (`OperationNotPermitted`) and block subnet/SG/VPC deletion until the platform releases them, so a teardown script must retry rather than fail.

## A2A runtimes

- **The container's own root paths are served under `/invocations`.** An `A2A` container binds port 9000 and serves `POST /`, `GET /.well-known/agent-card.json`, `GET /ping`; through AgentCore those become `POST …/invocations?qualifier=DEFAULT` and `GET …/invocations/.well-known/agent-card.json?qualifier=DEFAULT` (measured, both answered). The card is **not** at the domain root — `…/runtimes/<arn>/.well-known/agent-card.json` returns 404.
- **The Agent Card is behind the authorizer, so public discovery is impossible.** No `Authorization` → `401 MissingAuthenticationTokenException`; an invalid bearer → `403`; only a token from the configured pool returns the card. Worth knowing because standard A2A assumes a peer can read the card anonymously to learn what an agent does. Hosting the card statically (CloudFront) while keeping the RPC behind the authorizer is the way out, if open discovery is ever wanted.
- **A no-bearer request never reaches the container.** The `CUSTOM_JWT` authorizer rejects it at the edge, so an executor's own "you presented no identity" branch only guards a direct-to-container call — it cannot be exercised through AgentCore.
- **`message/send` needs `enable_v0_3_compat=True`** on `create_jsonrpc_routes`; without it the endpoint answers "Method not found" to the method AWS documents and standard clients call. In v0.3 the role is `"user"`, not `"ROLE_USER"`.
- **`Authorization` must be allowlisted** (`requestHeaderConfiguration.requestHeaderAllowlist`) or the adapter sees no bearer to forward and refuses every task.

## mcpServer target wiring gotchas

- **The target endpoint must be the full URL-encoded runtime ARN** (`https://bedrock-agentcore.<region>.amazonaws.com/runtimes/<urlencoded-arn>/invocations?qualifier=DEFAULT`), not the bare runtime id — otherwise target creation FAILS with "accountID is required".
- **The target caches the downstream MCP handshake at creation.** After upgrading the server image, delete and recreate the target so the gateway re-handshakes.
- **The downstream MCP server must speak the gateway's locked MCP protocol version.** A gateway pinned to `2025-11-25` rejects a server that only negotiates older versions; `update-gateway` cannot add protocol versions to an existing gateway (recreate it). For the Python `mcp` SDK, `2025-11-25` requires `mcp >= 1.23.0`.
- **`mcpToolSchema` removes the creation-time credential problem.** Without it, a `mcpServer` + `AUTHORIZATION_CODE` target enters `CREATE_PENDING_AUTH` and needs one operator consent under a synthetic userId, purely so the Gateway can list tools when no user is present. Supply the schema and the pre-auth disappears (verified: straight to `READY`). Format gotcha: `inlinePayload` is a JSON **string** containing `{"tools":[…]}`; a bare array fails with `mcpToolSchema must be an object with 'tools' array`. A target stuck in `CREATE_PENDING_AUTH` **cannot be deleted** — use `UpdateGatewayTarget`.

## Client contract for calling a Gateway MCP endpoint directly

- Send `MCP-Protocol-Version: <version>` on **every** request after `initialize` (the gateway is otherwise stateless about it and falls back to an older version, 400 `-32042`).
- Tool names are target-prefixed: `<targetName>___<toolName>`.

## The credential-delivery limit that shapes this repo

This is the one identity-adjacent finding kept here, because it decides the topology: **a Runtime-hosted MCP server cannot be handed a per-user token by the Gateway.**

Single-variable experiment: **one** gateway (`CUSTOM_JWT` inbound), **one** synthetic identity, **one** permission set, three targets differing only in type and outbound credential. Same `CustomOauth2` provider, scopes, `grantType` and return URL on both OAuth targets.

| Target | Outbound | Gateway → downstream | Container saw | User token |
|---|---|---|---|---|
| OpenAPI (external HTTPS) | OAuth 3LO | ✅ | n/a | ✅ real user data returned |
| Runtime `mcpServer` | OAuth 3LO | ❌ `MCP initialization failed: Authorization error when sending message` | nothing (only platform health-check pings) | ❌ |
| Runtime `mcpServer`, same runtime | SigV4 | ✅ full handshake + `tools/call` | `auth=(none) token=no` | ❌ |

**Mechanism:** the Runtime `/invocations` endpoint authenticates the transport itself and owns the `Authorization` header. With SigV4 outbound the header is spent on the signature and stripped before the container; with OAuth outbound the Bearer replaces the signature and the front door rejects the call. Either way the container cannot be handed a per-user bearer by the Gateway. Also note `credentialProviderConfigurations` is fixed at **one** item, so `GATEWAY_IAM_ROLE` and `OAUTH` are mutually exclusive per target — and on a Runtime target that single slot is already spent on the transport, which makes the two rows above exhaustive rather than merely inconvenient.

Two controls, because permission gaps had already produced several wrong conclusions in this investigation:

- The **SigV4 target on the same runtime succeeded**, returning our own server's `no user token (authorize first)` string — so `InvokeAgentRuntime` and the Gateway→Runtime path both worked.
- Re-run with `bedrock-agentcore:*`, `secretsmanager:*`, `bedrock:*`, `kms:*`, `sts:*` on `Resource: "*"`: **byte-identical failure**, while the OpenAPI target still succeeded. The result is permission-independent.

**Consequence:** our tool servers run on Runtime, so the agent fetches each user's token itself and passes it in a custom passthrough header. The managed Gateway path becomes available only by moving the server onto an addressable HTTPS endpoint (ALB / API Gateway / Fargate), trading Runtime's session and scaling model for it.

**And the corollary that saves days: when a Gateway OAuth target fails, suspect the gateway execution role before suspecting the feature.** Per-user 3LO *does* work for a `CustomOauth2` provider on an addressable target — but the role needs both `bedrock-agentcore:GetResourceOauth2Token` / `GetWorkloadAccessToken*` **and** `secretsmanager:GetSecretValue` on `bedrock-agentcore-identity!default/oauth2/*` (fetching reads the provider's managed secret *as the caller*). Missing either returns one opaque string — `An internal error occurred. Please retry later.` — that reads exactly like a missing capability. A Runtime target additionally needs `InvokeAgentRuntime`, with the same opaque symptom. Also: `3LO outbound requires CUSTOM_JWT inbound` (an `AWS_IAM` gateway refuses the target outright: `ValidationException: 3LO Auth is not supported when gateway authorizer type is AWS_IAM`), and vault keys derived from `ForUserId` vs `ForJWT` are **separate namespaces**, so migrating between them silently costs every user one re-consent. The full narrative, the per-variable permission matrix and the misdiagnosis history are in the sibling identity samples linked at the top.
